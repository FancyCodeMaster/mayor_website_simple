# Internationalization (Nepali / English)

Bilingual support touches routing, SEO, content, and the toggle. Read this
before touching any of them.

## 1. URL structure (unchanged)

**Nepali is the default locale, unprefixed; English is under `/en`.**
`/work/some-project` is Nepali, `/en/work/some-project` is English for the
*same* item (shared slug, `content.md` §2).

This is an SEO decision: search engines index URLs, not toggle states, and
a shared link should show the language the sender saw. Nepali is
unprefixed because it's the primary audience.

## 2. The toggle

`LanguageToggle` is a single visible control ("EN" / "नेपाली"). It is a
plain `<a href>` to the equivalent URL in the other locale, computed at
build time by a small pure function in `lib/i18n.ts` (add or remove the
`/en` prefix). A tiny script appends the current `location.hash` and query
string on click, so the anchor section and any `ListFilter` selection
carry over.

It is a real page navigation (fast, static HTML), chosen over a JS-only
content swap so both languages are properly indexable.

## 3. hreflang

Every public page emits via `HreflangLinks.astro`:

```html
<link rel="alternate" hreflang="ne" href="https://site/work/slug" />
<link rel="alternate" hreflang="en" href="https://site/en/work/slug" />
<link rel="alternate" hreflang="x-default" href="https://site/work/slug" />
```

`x-default` points at the Nepali URL. Always emit both alternates, even if
one language is currently fallback content. Each page's `canonical` is
**self-referencing**; never canonicalize one language to the other.

## 4. Fallback when only one language is filled in

**Decided: soft fallback, not a build error.**

- `pick()` (`content.md` §8) returns the other language when the requested
  one is empty, with `isFallback: true`. The page shows a small
  "English translation coming soon" note (or the Nepali equivalent).
- The only hard requirement is "at least one language" for required
  fields (`content.md` §7). Full bilingual completeness is encouraged, not
  enforced, so a time-sensitive item never waits on a translation.

## 5. Fixed UI copy vs. JSON content

- **Content** (Work, Updates, profile, municipalities) is bilingual in the
  JSON files (`{ en, np }`).
- **Fixed UI copy** (nav labels, button text, form labels, error messages)
  lives in `src/locales/en.json` and `src/locales/ne.json`, loaded by
  `lib/i18n.ts` from the route's locale. That's code, changed via a PR.

The content key is `np`; the locale code used in URLs, `hreflang`, `<html
lang>`, and `Intl` is `ne`. `lib/i18n.ts` owns that mapping in one place.

## 6. Editing bilingual content

Every bilingual field in the JSON sits next to its pair (`en` then `np`),
so filling in both languages for one item is a single edit in one place.
Leave a language as `""` (or `[]` for body) until the translation is ready.

## 7. Dates and locale formatting

Dates are ISO strings, formatted for display with `Intl.DateTimeFormat`
(`'ne'` or `'en'`). No Bikram Sambat conversion in v1. It's a distinct,
non-trivial feature, flagged here so it can be decided for v2.
